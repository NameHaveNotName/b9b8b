## P0：工作流媒体预签名 URL 会永久过期（继续批次已修复）

- 状态：**已修复新写入与主要消费链路**。分镜导入/生成和尾帧生成会同时保存稳定 `storageKey`；分镜读取、尾帧、直生视频和宣传片在使用媒体前按 key 重新签发 URL。
- 原因：R2/S3 预签名 URL 最长仅 7 天，但原实现把 URL 永久写入 `WorkflowStep.outputData`，过期后前端图片和传给供应商的参考帧都会返回 403。
- 兼容：历史数据若只有 URL、没有 `storageKey`，仍保留原值而不破坏记录；此类数据需要从关联 Asset 回填或重新导入后才能永久修复。
- 部署前置：`20260915000000_add_workflowstep_updated_at` 已于 2026-09-30 应用于生产 Supabase，并经 `prisma migrate status` 确认为最新。
- 验收：新导入/生成的分镜在原签名过期后仍能打开，并可继续生成尾帧和视频；Asset 中的 key 与 outputData 中的 key 一致。

- 证据：`lib/group-contributions.ts` 把时间范围内每一条非参考 Asset 都计为一个“生成结果”，包括未采用/被替换的历史版本；资产缺少 `createdById` 时又回退给关联操作用户，最后回退给项目 owner。项目中仍有多条 Asset/VideoSegment 创建路径没有写 `createdById`，因此大量旧资产可能集中归到项目所有者，且重复版本会把结果数推高到数百。
- 待办：
  - “有效贡献”按当前采用的业务目标去重（如 `project + step + act + shot + frame-role`），不以 Asset 行数代替。

  - 所有生成、导入、视频片段创建路径强制写入实际操作者；禁止缺失时默认归属项目 owner。
  - 为历史数据提供可审计回填：优先 OperationResult/OperationLog，其次可信 metadata；无法确定的标记“未知”，不猜归属。
  - 用用户所述异常成员/项目做数据对账，并加入同一镜头多次重生成的回归测试。
- 验收：同一镜头生成 20 个版本但最终只采用 1 个时，有效贡献只计 1；未知归属不计入任何成员；汇总可下钻到唯一业务目标。
