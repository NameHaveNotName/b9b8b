这是一个典型的**后端异步任务成功但状态未同步**问题。生图实际已完成（供应商侧确认 3 个成功，资产库已入库 2 个），但前端轮询读取到的状态仍是 `processing` 或超时。

---

## Kimi Code 执行提示词

**任务：修复人物设计步骤"后端生图成功但前端显示超时"的状态同步问题**

---

### Phase 1: 检查后端生图完成后的状态更新逻辑

1. 打开人物设计生图 API（通常是 `app/api/character/generate-images/route.ts` 或类似路径）。
2. 找到生图循环/队列处理完成后的代码段。
3. **关键检查**：当所有角色的图片都生成完成（或逐个完成）后，后端是否执行了以下操作：
   - 更新 `Project` 表的人物设计状态字段（如 `step_character_done = true` 或 `characterStatus = 'completed'`）
   - 更新生成队列中的任务状态（如 `status = 'completed'`）
   - 触发前端轮询可感知的任何状态变更
4. **排查点**：
   - 如果使用了异步队列（如 `generateQueue`），确认队列的 `onCompleted` 或 `job.finished()` 回调中确实写了状态更新
   - 如果使用了 `Promise.all` 并发处理，确认 `Promise.all` 的 `then` 或 `finally` 块中有状态更新
   - 检查状态更新是否被错误地放在了 `try` 块之外，或在某个条件分支中被跳过

---

### Phase 2: 检查前端轮询读取的状态字段

1. 打开人物设计前端组件，找到轮询逻辑（`useEffect` + `setInterval` 或 SWR）。
2. 确认前端轮询的是哪个状态字段：
   - 如果是 `project.characterStatus`，检查后端是否更新了这个字段
   - 如果后端更新的是 `project.step_character_done`，但前端读的是 `project.characterStatus`，就会出现状态不一致
3. **修复**：统一前后端状态字段命名，或让前端同时检查多个字段。

---

### Phase 3: 检查资产入库与状态更新的时序

**已知现象**：
- 供应商侧：3 个生图成功
- 资产库：已出现 2 个

**排查**：
1. 后端是**每生成一张图就立即更新状态**，还是**等全部生成完才批量更新**？
   - 如果是批量更新，中间任何一张图失败可能导致整个状态更新被跳过
   - 建议改为**每成功一张就更新进度**（如 `characterProgress: 2/3`），全部完成后标记 `completed`
2. 检查资产入库逻辑和状态更新逻辑是否在同个事务中：
   - 如果资产入库成功，但状态更新在另一个异步操作中失败，就会出现"有图但状态不对"
3. 检查数据库写入是否有并发冲突：
   - 如果多个角色同时完成，同时写 `Project` 表，是否出现竞态条件？

---

### Phase 4: 增加"强制刷新/状态校准"机制

在人物设计卡片上增加一个**"刷新状态"**按钮（或自动校准）：
1. 点击时前端调用 `GET /api/project/[id]/status` 或专门的状态校准 API
2. 后端该校准 API 逻辑：
   - 查询资产库中该项目的角色图片数量
   - 如果图片数量 ≥ 角色数量，强制将 `characterStatus` 设为 `completed`
   - 返回最新状态给前端

---

### Phase 5: 验证

1. 新建项目，进入人物设计步骤，触发角色生图。
2. 观察供应商侧确认生图成功。
3. 观察资产库确认图片入库。
4. 确认前端人物设计卡片从"进行中"变为"已完成"，不再显示超时。
5. 如果仍超时，点击"刷新状态"按钮，确认能强制校准。

---

**执行顺序**：Phase 1（后端状态更新）→ Phase 2（前端轮询字段）→ Phase 3（时序与并发）→ Phase 4（校准机制）→ Phase 5（验证）。

**先执行 Phase 1，确认人物设计生图完成后，后端是否调用了状态更新。**
