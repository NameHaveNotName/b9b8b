## 问题描述

风格统一步骤点击"重试"后，前端持续显示"进行中"（90%，已 184 秒），但**后端没有触发任何提示词生成**，也**没有向供应商发送生图请求**。供应商侧（小米 API）只记录了 deepseek-chat 的文本调用，**没有任何生图模型（gpt-image-2 / 即梦 / Flux）的调用记录**。这说明重试逻辑没有走到提示词生成或生图调用的代码路径。

## 猜测排查方向

1. **重试按钮的 onClick 没有调用正确的执行函数**：重试按钮可能只重置了前端状态（`setError(null)`），但没有重新触发后端 API 调用。
2. **提示词生成与生图是两个分离的 API，重试只调用了其中一个**：重试可能只调用了生图 API，但生图 API 依赖提示词生成 API 先完成。如果提示词不存在，生图 API 直接返回错误或被跳过。
3. **提示词生成 API 被条件判断跳过**：重试时，后端发现 `style_prompts` 字段已存在（即使是空的或旧的），认为不需要重新生成提示词，直接跳到生图阶段，但生图阶段又发现提示词无效，导致整个流程卡住。
4. **异步队列状态未清理**：重试时，生成队列中仍有之前失败的任务状态，新任务被队列阻塞，没有实际执行。
5. **Vercel 函数超时导致请求中断**：提示词生成或生图 API 在 Vercel 端执行超过 10 秒（Hobby）或 60 秒（Pro）被强制终止，前端轮询仍在进行，但后端已无任务。

## Kimi Code 执行提示词

**任务：排查风格统一"重试后提示词未生成、生图未调用"的系统性问题**

---

### Phase 1: 检查重试按钮的 onClick 逻辑

1. 打开风格统一步骤的前端组件，找到"重试"按钮的 `onClick` 处理函数。
2. 确认重试按钮点击后**实际调用了哪个 API**：
   - 是 `/api/style/generate`（全流程：提示词+生图）？
   - 还是 `/api/style/generate-images`（仅生图，假设提示词已存在）？
   - 还是 `/api/style/generate-prompts`（仅提示词）？
3. **关键检查**：如果重试调用的是 `generate-images`，但该 API 内部要求先调用 `generate-prompts`，就会导致提示词为空时直接失败。
4. 在重试的 fetch 调用前后加 `console.log`：
   ```ts
   console.log('[RETRY] Calling API:', apiUrl, 'with body:', body);
   ```
5. 检查浏览器 Network 面板，确认重试时发出了 POST 请求，且请求 body 不为空。

---

### Phase 2: 检查风格统一后端 API 的完整流程

1. 打开风格统一的主执行 API（如 `/api/style/generate/route.ts`）。
2. 画出该 API 的完整执行链路：
   ```
   接收请求 → 鉴权 → 读取项目数据 → [提示词生成?] → [生图调用?] → 返回结果
   ```
3. **检查条件分支**：
   - 是否有 `if (project.style_prompts)` 的判断，导致已有 prompts 时跳过提示词生成？
   - 如果有，确认 `style_prompts` 字段在数据库中的实际值。如果它是空数组 `[]` 或空字符串 `""`，条件判断可能误判为"已存在"。
4. **检查提示词生成函数**：如果提示词生成被封装为独立函数，确认该函数在重试时是否被调用。
5. 在 API 入口加日志：
   ```ts
   console.log('[STYLE-API] Received request for project:', projectId);
   console.log('[STYLE-API] Current prompts:', project.style_prompts);
   console.log('[STYLE-API] Will generate prompts:', !project.style_prompts);
   ```

### Phase 3: 检查提示词生成与生图之间的衔接

1. 如果提示词生成是**异步/队列任务**（如使用 BullMQ / Inngest / Vercel Cron）：
   - 检查重试时是否重新入队
   - 检查队列中是否有死任务阻塞新任务
2. 如果提示词生成是**同步顺序执行**：
   - 检查 `generatePrompts()` 的返回值是否被正确传递给 `generateImages()`
   - 检查 `generatePrompts()` 失败后，`generateImages()` 是否被跳过（如 `if (!prompts) return;`）
3. 检查提示词生成失败时，错误是否被正确抛出并返回给前端，而不是静默吞掉。

---

### Phase 4: 检查数据库状态对重试的影响

1. 在 Supabase SQL Editor 查询该项目的风格统一相关字段：
   ```sql
   SELECT style_prompts, style_status, style_images, updated_at
   FROM "Project"
   WHERE id = '项目ID';
   ```
2. **关键判断**：
   - 如果 `style_prompts` 为 `null` / `[]` / `""`：说明提示词从未生成，重试应该触发提示词生成
   - 如果 `style_prompts` 有旧数据：重试可能误判为"已有提示词"而跳过生成
   - 如果 `style_status` 为 `'processing'`：重试可能被状态锁阻止
3. 如果状态字段干扰重试，修改重试逻辑：重试时**强制重置**状态字段（如 `style_status = 'pending'`, `style_prompts = null`），然后重新执行完整流程。

---

### Phase 5: 检查 Vercel 函数超时与日志

1. 打开 Vercel Runtime Logs，筛选该项目的风格统一 API 路径。
2. 检查重试时是否有该 API 的日志记录：
   - 如果有，但执行时间很短（<< 1 秒）→ 说明 API 被提前 return 或 throw
   - 如果有，但执行时间达到 Vercel 上限 → 说明函数超时，任务未完成
   - 如果没有 → 前端请求根本没发到后端（可能是路由错误或中间件拦截）
3. 如果函数超时，将风格统一改为**异步队列模式**：
   - API 立即返回"任务已提交"
   - 实际提示词生成和生图在后台队列中执行
   - 前端通过轮询获取进度

### Phase 6: 修复重试逻辑

**目标**：重试时必须走完整的"提示词生成 → 生图"流程，不能跳过任何一步。

   ```ts
   const handleRetry = async () => {

     const res = await fetch('/api/style/generate', {

       }),
     });
     // ...
   };
   ```
2. 修改后端 API，支持 `forceRegenerate` 参数：
   - 如果 `forceRegenerate = true`，忽略数据库中已有的 `style_prompts`，重新生成
   - 重新生成提示词后，再执行生图
