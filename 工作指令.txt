概念图步骤报错 `WORKFLOW_002`，控制台显示请求 `body: undefined`，说明前端发送了**空请求体**给后端，或者后端对概念图步骤有前置条件检查未通过。

---

## Kimi Code 执行提示词

**任务：排查概念图步骤 `WORKFLOW_002` 错误**

---

### Phase 1: 定位错误码定义

1. 全局搜索项目中 `"WORKFLOW_002"` 字符串，找到定义该错误码的文件。
2. 确认该错误码的触发条件，常见可能：
   - 前置步骤未完成（如框架搭建未生成幕结构/环境设定）
   - 请求参数缺失（如 `projectId`、`acts`、`scenes` 等）
   - 风格图未选定（概念图需要基于风格统一的视觉风格）
   - 数据库中该步骤的状态字段异常

---

### Phase 2: 检查前端请求

1. 打开概念图步骤的前端执行逻辑（点击"开始执行"或"生成概念图"的 `onClick`）。
2. 检查 POST 请求的 body：
   - 控制台显示 `body: undefined`，说明前端可能**没有正确构造请求体**
   - 检查 fetch/axios 调用中 `body: JSON.stringify(...)` 是否遗漏，或传入的参数为 `undefined`
   - 检查请求头 `Content-Type: application/json` 是否正确设置
3. 检查请求 URL：是否正确指向概念图 API（如 `/api/concept/generate` 或 `/api/projects/.../concept`）。

---

### Phase 3: 检查后端 API 校验

1. 打开概念图 API 文件（如 `app/api/concept/route.ts` 或 `app/api/projects/[id]/concept/route.ts`）。
2. 检查请求体校验逻辑（如 Zod schema 或手动检查）：
   - 是否要求某些字段（`acts`、`styleImage`、`projectId`）必须存在？
   - 如果字段缺失，是否返回 `WORKFLOW_002`？
3. 检查前置条件校验：
   - 是否检查 `project.step_framework_done = true`？
   - 是否检查 `project.style_prompts` 或 `selectedStyleImage` 存在？
   - 如果前置条件不满足，返回的具体错误码是什么？

---

### Phase 4: 检查数据链路

**概念图生成通常需要以下输入**：
- 项目 ID
- 幕结构（每幕的场景描述）
- 选定的视觉风格/风格图
- 角色设定（可选）

**排查**：
1. 检查 `Project` 表中该项目的数据：
   - `framework` 字段是否有 `acts` 数组？
   - `selectedStyleImage` 或 `styleImageUrl` 是否有值？
2. 如果框架搭建的幕结构数据存储在 `Project.framework.acts` 中，确认概念图 API 读取的路径正确。
3. 如果风格统一步骤完成后没有把风格图同步到 `Project` 表，概念图 API 会因缺少风格参考而报错。

---

### Phase 5: 修复与验证

1. 如果是前端 body 为空，修复请求构造逻辑，确保发送正确的 JSON body。
2. 如果是后端前置条件检查过严，确认概念图真正必需的字段，放宽非必要限制（或给默认值）。
3. 如果是风格图未同步，修复风格统一 → 概念图的数据传递链路。
4. 本地测试：完成框架搭建和风格统一后，进入概念图，点击生成，确认不再报 `WORKFLOW_002`。

---

**执行顺序**：Phase 1（定位错误码）→ Phase 2（前端请求）→ Phase 3（后端校验）→ Phase 4（数据链路）→ Phase 5（修复）。

**先执行 Phase 1，全局搜索 `WORKFLOW_002`，找到触发该错误的具体代码位置。**
