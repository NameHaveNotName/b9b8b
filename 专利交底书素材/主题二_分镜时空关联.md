# 主题二：影视分镜数据的时空关联可视化与重排序方法

> 检索范围：`app/(dashboard)/project/[id]/storyboard/**`、`app/api/projects/[id]/steps/storyboard/route.ts`、`app/api/projects/[id]/steps/framework/route.ts`  
> 检索关键词：`storyboard`、`Shot`、`shotId`、`actNumber`、`sceneName`、`duration`、`DndContext`、`SortableContext`、`arrayMove`、`StoryboardTable`、`StoryboardCanvas`、`referenceImageUrl`、`firstFrameUrl`、`lastFrameUrl`、`mode`

---

## 技术问题

### 现有技术的不足

通用表格或看板工具虽然支持拖拽排序，但无法表达影视分镜特有的时空关系：

1. **缺少与幕结构（Act）的绑定**：分镜不是孤立卡片，必须明确属于第几幕，才能按叙事结构组织。
2. **拖拽后镜头序号与顺序不一致**：普通列表拖拽只改变数组索引，不会同步更新代表叙事时序的镜头标识。
3. **表格/画布双视图数据不同步**：表格侧侧重编辑字段，画布侧侧重可视化预览，两者若数据源分离容易不一致。
4. **缺少“视频生成 / 实拍参考”双模式字段**：同一分镜在不同阶段可能使用首帧图或参考图，需要模式化字段支持。
5. **分镜数量需按幕动态计算**：不同幕的叙事权重不同，不能简单平均分配镜头数。

本系统通过 `Shot` 数据结构、`StoryboardTable` / `StoryboardCanvas` 双视图、`Dnd-kit` 拖拽，以及幕结构驱动的分镜生成逻辑，解决了上述问题。

export interface Shot {

  const { active, over } = event
  if (over && active.id !== over.id) {
    const oldIndex = shots.findIndex((s) => s.shotId === active.id)
    const newIndex = shots.findIndex((s) => s.shotId === over.id)

## 技术效果

1. **分镜数据具备时空属性**：`Shot` 接口通过 `actNumber`、`sceneName`、`duration`、`cameraMove` 等字段，把每个镜头绑定到幕-场景-时长的叙事坐标系中。
2. **拖拽改变叙事顺序**：`StoryboardTable` 使用 `@dnd-kit` 实现垂直拖拽，`arrayMove` 调整数组后通过 `saveShots` 同步到后端，`localShots` 变更会同步到画布视图。
3. **双视图数据同源**：`StoryboardPage` 用 `localShots` 作为单一数据源，表格视图修改后画布视图实时同步，避免两套数据分裂。
4. **按幕动态生成分镜**：`generateStoryboardByAct` 为每一幕独立调用 LLM，并传入 `ESTIMATED_SHOTS` 和 `ACT_PACING`，使镜头数量与节奏符合幕结构需求。
5. **幕-镜头关联可统计**：`actsSummary` 按 `actNumber` 统计每幕实际镜头数，为后续片段合成、宣传片剪辑提供结构依据。
6. **双模式画面兼容**：`referenceImageUrl` / `firstFrameUrl` / `lastFrameUrl` 支持实拍参考、视频生成、首尾帧三种画面来源，并通过 `mode` 字段在表格/画布中切换显示。

## 证明“非通用卡片列表”的核心证据

- `Shot` 接口包含影视专用字段：`actNumber`、`sceneName`、`cameraMove`、`duration`、`characters`、`referenceImageUrl` / `firstFrameUrl` / `lastFrameUrl`。
- 生成逻辑按 `framework.acts` 逐幕调用 LLM，并传入 `ESTIMATED_SHOTS`、`ACT_PACING`、`KEY_SCENES`。
- 保存后生成 `actsSummary`，统计每幕镜头数，直接用于后续视频合成管线。
- 双视图切换时共用 `localShots`，且均受 `shotMode` 控制，保证实拍参考/视频生成两种制作模式的一致性。
